# litus 進捗の半自動レポート（2日おき）設計

作成日: 2026-07-08
対象: モバイルアプリ「リタス（Litus）」の開発進捗を、数日おきに①自分用ダイジェスト②X投稿下書き③公開devlogの3種として半自動で用意する仕組み。

## 背景・目的

litus は別リポジトリ（ローカル `C:\dev\litus` ／ リモート `github.com/waiteu-git/litus`）で開発中。公開前の期待維持（X・事前登録者）と、複数セッションにまたがる開発の自分用把握のため、**進捗を定期的に3方向へ伝える**手段が欲しい。

方針（ユーザー確定）:
- **チャネル = 3つ**: X投稿下書き／ランディングの公開devlog／自分用ダイジェスト。1つの生成から3方向に出す。
- **モード = 半自動**: 生成は自動、公開はレビュー後。公開ページを未チェックで自動デプロイはしない。
- **周期 = 2日おき**。
- **届け先 = Discord プライベート管理チャンネル**（既存 ops-automation の Discord 投稿を流用）。
- **定期実行 = 案B: スケジュールされたクラウドルーティン**（`/schedule`）。デスクトップの無人claude許可に依存しない自己完結型。
- **devlog = 専用ページ `updates.html`**（`/app` から「開発の歩み」で導線）。/app 本体は肥大させない。

備考: 2026-07-06〜のブランド改名（Litas→Litus）に伴い、旧 `C:\dev\litas` はローカルで `C:\dev\litus` に改名済み。ソースは litus を指す。

## スコープ確定

**含む:**
- litus の差分（前回処理点以降の git log ＋ CHANGELOG）を集める仕組み
- 3種の下書き生成（自分用ダイジェスト／X下書き／devlogエントリ）
- Discord 管理chへの投稿（Webhook）
- 公開 devlog ページ `landing/updates.html`（翠テーマ・日付エントリ積み上げ・`/app` から導線）
- 2日おきのスケジュール実行（クラウドルーティン）

**含まない（YAGNI / 後送り）:**
- 事前登録者へのメール配信（今回のチャネルに含めない。将来別途）
- devlog の自動デプロイ（半自動なのでレビュー後に反映）
- X の自動投稿（不可・下書きのみ）
- 多言語化・凝った devlog デザイン

## アーキテクチャ

疎結合な小さな単位に分ける。**決定論的な部品（収集・投稿）＋ LLM 生成ステップ**。

```
[2日おき スケジュール（クラウドルーティン / 案B）]
        │ 実行
        ▼
1. 収集: litus を取得（clone/pull）→ 前回SHA以降の git log ＋ CHANGELOG差分を構造化テキストに
        │ 差分ゼロなら「今回スキップ」（空投稿しない）
        ▼
2. 生成(LLM): 構造化テキスト → 下書き3種
     (a) 自分用ダイジェスト（出た/進行中/次）
     (b) X投稿 下書き（ハイライト1本・必要ならスレッド）
     (c) devlog エントリ（日付つき・公開用の整文）
        ▼
3. 投稿: Discord 管理ch（Webhook）へ 3種をまとめて投稿
        ▼
4. 状態更新: 最後に処理した litus コミットSHAを保存（次回の差分起点）
```

公開（レビュー後・人手/私が補助）:
- X → Discordの下書きをコピペ投稿（ユーザー）
- devlog → ユーザーが「この回出して」→ 承認エントリを `landing/updates.html` に追記 → push で Cloudflare 自動デプロイ（私が実行可）
- 自分用ダイジェスト → Discord に残る（記録）

### 部品と責務

- **収集スクリプト**（決定論・テスト可）: 入力=前回SHA、出力=`{ commits: [...], changelogAdded: "...", newestSha }`。litus の `git log <lastSha>..HEAD` と CHANGELOG の差分を整形。差分なし時は空を返す。
- **状態**: `ops/litus-devlog/state.json`（`{ lastSha, lastRunAt }`）。周期実行をまたいで永続化するためリポジトリにコミット。
- **生成（LLM）**: 収集出力を受け、3種の下書きを一定フォーマットで書く。X/devlogのトーンは既存のランディング文体（LETUSもCLASSも…／煽り過ぎない）に合わせる。ハルシネーション防止のため**収集した実データ（コミット/CHANGELOG）以外の新機能を主張しない**。
- **Discord投稿スクリプト**（決定論）: Webhook URL（`DISCORD_DEVLOG_WEBHOOK`）へ POST。3種を読みやすく整形（Discordの2000字制限に配慮し分割可）。
- **devlogページ** `landing/updates.html`: 日付エントリのリスト。新エントリは先頭に追記。`/app` に「開発の歩み →」リンクを追加。

## データフロー・状態

- 差分起点 = `state.json.lastSha`。初回（state無し）は**直近7日分のコミットを起点**にする（以降は毎回 `lastSha` を追従）。
- 実行後、`lastSha = newestSha` に更新しコミット（クラウドルーティンが repo に push、または state をリポジトリ管理）。
- devlog公開はレビュー後なので、`state.lastSha` の前進（=Discordに届けた点）と、実際に `updates.html` に載った点は別管理でよい（スキップした回のcommitも次回ダイジェストには含めない＝Discordで一度は見えているため）。

## エラー処理

- litus 取得失敗 → その回はスキップ、Discordにエラー通知（サイレント失敗させない）。
- 差分ゼロ → 「今回は更新なし」を短く通知 or 無投稿（設定で選択、既定=無投稿）。
- Discord投稿失敗 → リトライ1回、だめなら次回に持ち越し（state は前進させない）。
- 生成が実データ外の主張をしないよう、生成プロンプトに「収集データに無い機能を書かない」制約を明記。

## 段階導入（フェーズ）

- **フェーズ①（コア・手動実行）**: 収集スクリプト＋`updates.html`＋Discord投稿スクリプト＋状態管理。実行はオンデマンド（「今回分やって」で私 or 手動が collect→LLM生成→Discord投稿）。これだけで「叩けば3種が出てDiscordに届く」が成立。
- **フェーズ②（自動化）**: 2日おきのクラウドルーティン（`/schedule`）でフェーズ①の一連を実行。デスクトップ非依存。

①だけで実用。②で無人化。実装計画はこの順で。

## 前提・要準備

- **Discord 管理専用チャンネル＋Webhook URL**（無ければ最初に作成。URLは環境変数 `DISCORD_DEVLOG_WEBHOOK` として保持）。
- クラウドルーティンが litus（private repo）と lms-task-watcher にアクセスできること（読み取り＝litus、書き込み＝state/landing は lms-task-watcher）。
- 生成のトーン基準＝既存ランディング文体・[[project_app_landing]]・ブランド[[project_app_branding]]。

## テスト

- 収集スクリプト: 固定の git ログ/CHANGELOG フィクスチャ → 期待する構造化出力（差分あり／差分ゼロ／複数コミット）。
- Discord投稿スクリプト: Webhook をスタブし、ペイロード整形と2000字分割を検証。
- devlogページ: preview で `updates.html` 表示・`/app` からの導線・エントリ追記が崩れないこと。
- 生成（LLM）ステップは決定論でないため、フォーマットの型（3セクション・実データ準拠）を人手レビューで担保。

## 棄却・保留

- 完全自動（devlog無レビュー自動デプロイ）→ 公開事故回避のため不採用。
- デスクトップ ops-automation（案A）→ 無人claude許可依存を避け、案B（クラウドルーティン）採用。
- メール配信チャネル → 今回スコープ外。
